# 하지 않기로 한 것과 이유

| 하지 않는 것 | 이유 |
| --- | --- |
| 센서(`/scan`) 끊김 감시 | 명령 쪽과 모터 쪽 고장을 끝까지(재현 → 수정 → 측정 → 공개) 하는 데 집중한다. 센서 끊김 감시는 다른 팀 프로젝트에서 다뤘다 |
| 안전 등급 기능이라고 주장 | 위험 분석과 인증을 거치지 않았고, 한 대 · 실내 · 저속 · 집 공유기 하나에서만 시험한다 |
| SLAM · 경로 계획 알고리즘 직접 개발 | 목표는 드라이버의 고장 대응이다. Nav2는 쓰는 대상이다 |
| 학습 정책을 시뮬에서 실물로 옮기기(강화학습 · 모방학습) | 이 프로젝트의 질문("고장 나면 로봇은 무엇을 하나?")과 거리가 멀다. 여기서 시뮬 · 실물 차이를 줄인다는 것은 차이를 재고 시뮬을 실측으로 맞추는 것이다 |
| 큰 학습 모델 | 하지 않는다. 끊김 예측(문턱 규칙과 작은 모델 견주기)도 끊김 기록이 충분히 모였을 때만 한다 |
| 실물 여러 대 | 로봇이 한 대다 |
| 통신망 쪽 제어(기지국에서 망을 다루는 것) | 통신사 장비의 일이다. 이 프로젝트는 로봇 쪽에서 통신 상태를 재고 대응한다 |
| 무거운 Gazebo 시험을 CI에서 매번 | GitHub 러너에 GPU가 없다. CI는 빌드와 단위 테스트, Gazebo 반복 시험은 노트북에서 반복 스크립트로 돌린다 |
| 자율주행 시뮬레이터(CARLA 등) | 이 프로젝트는 실물에 맞춘 작은 시뮬로 시뮬 · 실물 차이를 잰다. 차 규모의 시뮬레이터는 질문과 거리가 멀다 |
| Isaac Sim | 노트북 GPU(8GB)가 Isaac Sim 문서의 최소 사양(16GB)보다 작다. TurtleBot3 공식 시뮬인 Gazebo를 쓴다 |
